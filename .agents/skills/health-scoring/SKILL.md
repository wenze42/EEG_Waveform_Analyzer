# 项目健康度评分与重构诊断

> 核心理念：**不堆熵**——代码不是越多越好，结构越深越好。

本 Skill 参考 Ousterhout 的《软件设计哲学》中复杂性、深模块和信息隐藏原则，诊断项目的结构性设计债务。

## 适用范围

- 评估项目、某个 Spec 或 PR 的设计健康度、维护风险或仓库集成程度；
- 给出 H_L、F_R 或 0–100 分；
- 比较 Spec 完成时和 PR 合并前的评分变化。

不要把分数解释为"测试通过数"或"代码行数"——测试通过只能证明某条路径被验证，不能替代模块深度、信息隐藏或变化放大的判断。

## 六维评分框架

按以下六个维度评分（0–5 分），每维度权重可按项目调整：

| 维度 | 观察点 | 高分（4-5） | 低分（1-2） |
|------|--------|-------------|-------------|
| **模块深度** | 接口小、实现深 | USB 口式接口，调用者不关心内部 | 透传参数、暴露内部结构 |
| **信息隐藏** | 知识集中 | 规则只在一处定义 | 同一规则在多个模块重复 |
| **变化局部性** | 变化影响范围 | 小改动只触一个模块 | 改一处牵多处 |
| **边界清晰** | 模块边界 | 契约稳定、接口单一 | 跨层调用、职责重叠 |
| **错误/恢复** | 失败语义 | 统一错误、单一恢复路径 | 每层自行处理、恢复靠临时操作 |
| **可观测性** | 测试/CI/文档 | 契约级测试、失败可定位 | 只有 store 测试、失败靠猜 |

## 反通胀评分规则

按以下锚点评分，3/5 表示"能工作但有明显债务"，不是健康默认值：

- **5**：模块深、知识集中、变化局部；有持续度量、复盘和自动约束证明这一状态；
- **4**：边界和约定系统化，常见变化可以局部完成；仍有少量已知债务；
- **3**：主路径可用，但存在重复规则、人工协调、浅接口或未收敛的跨模块依赖；
- **2**（低分）：已观察到结构性放大——同一规则在多个模块重复、调用链透传实现细节，只能靠人工记忆或局部补丁维持；
- **1**（严重低分）：边界基本失效，调用者必须理解内部机制才能正确使用；
- **0**：缺失、互相矛盾，或无法提供可信证据。

关键维度低于 **2/5** 时必须标为**阻断风险**，低于 **3/5** 时必须给出**重构方向**。

## 工作流程

1. 确认 Git 根目录、当前 SHA、目标 Spec 或 PR，以及评分阶段（Spec 完成 or PR 合并前）；
2. 阅读当前 Spec、CONTEXT.md、GLOSSARY.md、相关接口契约、测试和 CI；
3. 分别计算 H_L（内部健康度）和 F_R（与宿主仓库/框架契合度）；
4. **先找缺陷再打分**：对每个二级指标记录变化放大点、知识泄漏、边界错位；
5. 每个低分项至少给一条可执行重构建议，格式为：

```
模块/边界 → 结构问题 → 重构动作 → 预期减少的变化放大 → 回归门槛
```

6. 报告健康等级、结构性不足、重构顺序和未覆盖风险。

## 重构优先级

按**复杂性降低收益**排序：

```
最高优先级 = 变化放大范围 × 变化频率 × 边界关键性
```

- 变化放大范围：一个小改动牵动多少模块；
- 变化频率：这类改动在项目中有多频繁；
- 边界关键性：这个边界涉及权限、并发、审计还是普通 CRUD。

## 证据与置信度

- **A 级置信度**：自动化测试、CI、可复现运行结果；
- **B 级置信度**：代码抽样、文档证据；
- **C 级置信度**：主要依赖未验证假设。

## 输出要求

默认输出：

- `H_L`：内部健康度 /100 和置信度；
- `F_R`：外部契合度 /100 和置信度；
- 六维分项表、低分二级指标和关键证据；
- 每个低分项的结构性不足与模块级重构方向；
- 按复杂性降低收益排序的最高优先级重构动作；
- Git SHA、Spec/PR、验证命令和未覆盖风险。
